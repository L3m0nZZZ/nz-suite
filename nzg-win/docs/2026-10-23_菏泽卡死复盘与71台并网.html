三、根因：两种"死法"

3.1 Windows：reconnect 让读取永不返回

/* ❌ 旧配置（看起来更"健壮"，实际是灾难） */
av_dict_set(&opts, "reconnect", "1", 0);
av_dict_set(&opts, "reconnect_streamed", "1", 0);

/* 失败链：分片/连接失败 → http 层无限重试且**永不返回错误**
 *   → av_read_frame 永久阻塞在 hls demuxer 内循环
 *   → 线程不报错也不退出，waveOut 队列播空 → 彻底静音
 *   → 看门狗判死，stop_play_thread 等 6 秒超时（Windows 不能强杀线程）
 *   → 每轮重建泄漏 1 线程 + 若干 socket → 累积半天后彻底不动 */
/* ✅ 现在：让失败快速冒泡 */
av_dict_set(&opts, "fflags", "nobuffer+discardcorrupt", 0);
av_dict_set(&opts, "seg_max_retry", "2", 0);      /* 分片失败 2 次就返回 AVERROR */
av_dict_set(&opts, "http_persistent", "0", 0);    /* 不复用长连接，挂死不伪装成"还在等" */
/* 故意不设 reconnect / reconnect_streamed */

原则：宁可报错重建，也不要无限重连。重建会重新解析拿新签名，比原地死等有价值。

3.2 安卓：纯音频台根本不判死（更隐蔽）

// ❌ 旧代码：videoFormat 对纯音频恒为 null → 整段判死逻辑被跳过
if (p.isPlaying && p.videoFormat != null) { ... pos 停滞检测 ... }

// ✅ 现在：只看 isPlaying + 位置是否前进
val pos = p.currentPosition
if (p.isPlaying) {
    if (pos != lastPosMs) { lastPosMs = pos; posStallTicks = 0 }
    else if (++posStallTicks * 5000L >= frameStallSec * 1000L) fail("播放位置停滞", stall = true)
}

广播场景绝大多数是纯音频流，这一条等于安卓版的"半天不动"从不自愈。已从 APK 字节码核实：videoFormat 引用数 = 0。

3.3 为什么表现是"半天"

单次故障在几十秒内就能恢复。但旧实现每次重建泄漏一个卡死的线程，而每次判死又会再建一个。 半天里积累几十次后，进程要么句柄耗尽、要么 waveOut 设备被占满，自愈彻底失效——表现就是"一直在播，但永远不动"。

五、参数决策：换票为什么要从 20 分钟改成 3 小时

v1.13 只有 30 分钟短测数据，保守取 20 分钟。六小时长测推翻了"票很短命"的假设：

项单县 FM88.8（orgid 155）巨野 FM94.1（orgid 139）
采样次数714714
时长5.99 h（08:45 → 14:45）5.99 h
HTTP 状态全部 200全部 200
失败计数恒 0恒 0
playlist 末片时间戳单调递增，跨度 6.0 h单调递增
采样断档 > 60 s0 次0 次

结论：同一签名 URL 有效期实测 ≥ 6 小时。而换票不是免费的——实测一次换票的音频空档是：

[15:02:26] [换票] 动态签名源已用 2 分钟，主动重新解析（阈值 90 秒）
[15:02:26] [重启] 播放器重建：动态源定时换票
[15:02:32] [播放] 开始播放：单县人民广播电台FM88.8    ← 空档 6 秒

6 秒大头是 100ycdn 每次给新域名、要重做 TLS 握手（2~2.5 秒）+ 首帧。于是：

周期每天换票次数每天静音结论
20 分钟（旧）72 次≈ 7 分钟纯损
3 小时（现）8 次≈ 48 秒对实测下界留 2 倍余量
6 小时4 次≈ 24 秒贴着下界，不建议

真过期也不怕：reconnect 已去掉，票失效会「报错 → 线程干净退出 → 看门狗重建」，最坏十几秒空档而不是卡死。所以周期宁可长。
