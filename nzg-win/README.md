# 守播广播 Windows 版（nzg-win）

Android 版「守播广播」（`com.shoubo.radio`，工程 `D:\ningz\nzg`）的 Windows 桌面版。

**单 exe、绿色便携、Win7 起**，内置 **72 个广播台**（v1.16.2，2026-11-03）：
基础清单来自 `_capture/nzg_本次清单72台_20261102.csv`，再并入安卓版逐条实测通过的台，
覆盖山东 55 / 河南 6 / 内蒙古 3 / 安徽 3 / 广东 3 / 陕西 2。
**启动后音量固定 100%**（不记忆上次；`state.json` 只记台号与静音状态）。

| 指标 | 值 |
|---|---|
| 体积 | **5.59 MB**（5,861,888 字节，单文件，静态链接） |
| PE 机架 | `pei-i386`（32 位，64 位系统走 WoW64 一样能跑） |
| 依赖 dll | 仅 Win7 自带：`KERNEL32 / USER32 / GDI32 / ADVAPI32 / SHELL32 / msvcrt / WINMM / WINHTTP / WS2_32 / ole32 / bcrypt / Secur32`（12 个 / 357 函数，`ole32` 是 v1.16 走 WASAPI 才用上的，`CoCreateInstance` + `CoInitializeEx` + `CoTaskMemFree` 全是 Vista 起就有） |
| 子系统 | Windows GUI（不闪黑窗） |
| 最低系统 | Windows 7 SP1（用 msvcrt 而非 ucrt，ucrt 要 Win10） |
| 频道自检 | **72/72 通过**，失败 0、跳过 0（v1.16.2 快检 `--selftest` 245.2 秒；活性 `--selftest --live` 399.0 秒，**在播 39 / 疑似垫片 0 / 无法判定 33**） |
| 长跑 | 12 分钟单台 **0 重建 / 0 断线 / 无静音空档 / 0 分片跳过**（鹤壁；同日单县因源站 502 有重建，已归因） |

## 一、直接用

1. 把 `守播广播.exe` 拷到任意目录（桌面、U 盘都行），双击启动。
2. 不需要安装、不依赖任何外部 dll。**会写一个 `HKCU\...\Run\ShouboRadioWin`**
   用于开机自启（v1.12 起，用户要求），路径跟随 exe 当前所在位置，无需管理员。
3. 32 位 exe 在 64 位 Win7/8/10/11 上一样能跑。

运行后会在 exe 同目录生成：

| 文件/目录 | 作用 |
|---|---|
| `logs/log-YYYY-MM-DD.txt` | 事件日志，按天分文件，自动保留 7 天 |
| `state.json` | 上次停在哪个台、音量多少（下次启动自动恢复） |
| `config.json` | **可选**，放了就会覆盖内置频道清单 |

### 升级到新版本（⚠️ 别只替换 dist）

本项目的 exe 是**放在版本归档目录里跑的**（`nzg_win_versions/vX.Y_N台_日期/`），
开机自启里写的是那个目录的**绝对路径**。所以：

> **只替换 `nzg-win/dist/守播广播.exe` 等于没升级** —— 自启项还指着旧归档目录，
> 重启后照样跑旧版（2026-10-23 踩过：dist 已是 v1.13，实际跑的却是 v1.12，
> 两个目录的日志混在一起，排障时极易被带偏）。

正确姿势用 `deploy.py`（幂等，带验证与自动回滚）。**不传 `--exe` 就自动选版本号最大的归档**
（以前这里写死过 v1.13，隔几个版本后不带参数跑会把老版本装回去）：

```bash
python deploy.py --copy-from dist/守播广播.exe   # 刚编译完：复制进最新归档再部署
python deploy.py --no-start                      # 只改自启不启动（先验链路时用）
python deploy.py --exe "D:\ningz\nzg_win_versions\v1.16.2_72台_20261103\守播广播.exe"
```

它做四件事：停旧进程 → 复制新 exe → 把自启项改指新路径（原值备份到
`run_key_backup.txt`）→ 启动并**核对「进程路径 + 日志里的版本号」双证据**；
对不上自动回滚到旧版并重启，不会把用户晾在无声状态。

启动用的是 `DETACHED_PROCESS`，理论上关掉终端不会带走程序；
但这条**没能在开发环境实证**，部署完建议关掉窗口等一分钟，确认托盘图标还在。

### 频道自检模式（部署前先跑这个）

```bash
守播广播.exe --selftest            # 快速自检，72 台约 3~5 分钟
守播广播.exe --selftest --live     # 额外做 HLS 活性探测，72 台实测约 7~8 分钟
```

不建窗口、不初始化声卡，按播放线程**同一套调用序列**（解析动态源 → 打开 → 探测流信息 →
选音频轨 → 开解码器 → 解出首帧）逐台跑一遍，结果写到 `dist/selftest.txt`：

```
[ 1/72] OK   mp3 48000Hz 2ch  [活性无法判定]
        河南  鹤壁综合广播FM93.5  auto
        https://lhttp.qtfm.cn/live/5022055/64k.mp3
        1812 ms
...
汇总：通过 72，失败 0，跳过 0，总耗时 399.0 秒
活性：在播 39，疑似垫片 0，无法判定 33
```

退出码：`0` = 全通过，`2` = 有失败台，`1` = 没失败但有跳过（多半断网）。
超时 10 秒/台逐包、最多 400 个包；
另有 **12 分钟总预算**兜底 —— 断网时单台的网络等待没有硬上限，没有这个预算
72 台全卡住能拖到半小时以上，会让人以为程序挂死了。超预算的台标 `SKIP` 并写明原因，不假装通过。
（v1.16.2 含 `--live` 实测 399.0 秒，12 分钟预算还剩近一半；若网络普遍变慢，先看报告里有没有 SKIP。）

**失败会自动重试一次（并重新解析动态源）**，因为真实播放走的是退避重试、永不放弃的状态机，
单次采样判死会低估 litenews 这类三跳 HLS（实测冷连接每个新主机 TLS 就要 2.0～2.5 秒，
之后再连只要 0.1～0.4 秒 —— 常常只是冷连接慢，不是坏）。
重试才过的台会在报告里写明，例如：

```
[15/72] OK   aac 48000Hz 2ch（重试通过，首次 FAIL 打开流失败）
```

**换源、改台、出包之后跑一次**，能挡住绝大多数「看着配置对、其实拉不到流」的问题。

**2026-10-10 起，自检也会走镜像**：主源打不开 → 自动试 `backup_url` → 成功则报告
`OK（经镜像）` 并把生效 URL 换成镜像地址。所以「主源坏了但镜像活着」的台不会被冤枉成 FAIL。


### `--live`：活性探测，揪出「循环垫片」

`--selftest` 只证明「拉得开、能解出帧」。平台侧停推时常见做法不是撤流，而是留一段
**循环垫片**（frozen pad）—— 那种流照样过检，但人耳听到的是一段死循环。
`--live` 把源清单备注里那套人工判据自动化了：

> 隔几秒拉两次 HLS 媒体列表，看**最后一个分片的 unix 时间戳**跟不跟得上墙上时钟。

实现见 `src/liveness.c`，判据是**两条，任一成立即判在播**：

1. **最新分片的滞后量** `lag = 墙上时钟 - 分片时间戳`，`lag <= 300 秒` → 在播；
2. **分片时间戳在前进**：相隔 `target_duration+1` 秒采样两次 playlist，
   `Δts > 0`（或 `MEDIA-SEQUENCE` / 末片名变化）→ 在播。

两条都不成立（lag 大 **且** Δts=0）才判垫片。第 2 条是 2026-10-23 补的：
只用滞后量会把 **10 台真在播的台误报成垫片**（实测惠民 lag=2168 秒、昌邑 lag=21069 秒，
但 Δts=1~2 秒、playlist 正常滚动 —— litenews 的 `alivealone302` 域名分片名走服务器时钟，
比墙钟慢几小时不等于停推）。误报归零后，「在播」从 30 台升到 40 台。

历史实测对照（2026-10-10，45 台，当时只有第 1 条判据）：

| 结果 | 台数 | 说明 |
|---|---|---|
| 在播 | 22 | lag 0～140 秒 |
| **疑似垫片** | **3** | 临邑 FM92.1（lag **16.5 天**）、昌邑 FM103.3（lag **5.1 小时**）、莒县 FM97（lag **24 分钟**） |
| 无法判定 | 20 | 全是蜻蜓 mp3 直链，非 HLS，判不了 |

**真垫片的特征是「Δts=0 且 lag 一路涨」**（涨到几百秒 ~ 十几天）；
lag 大但 Δts>0 的是时间轴偏移，仍在播。改代码前先读 `liveness.c` 的文件头，
里面记了三个踩过的坑：

1. **不能**用「Δts 跟不跟得上墙钟」当判据 —— litenews 正常直播的分片名按 1 秒递增、
   而每片约 2 秒（`#EXTINF:1.997`），Δts ≈ 墙钟的 **0.5 倍**，会把正常台全判成垫片。
2. **不能**只用「Δts ≥ 1」当唯一门槛 —— 有些源一个分片十几秒，4 秒内 playlist 本来就不更新，
   Δts=0 但滞后只有 19 秒，那是在播的（陕西 snrtv 就是这样）。所以它是**补充判据**，不是替代品。
3. `LAG_MAX=300` 别轻易放宽：真有 CDN 缓冲超过 5 分钟的直播会被误判，但那种台本来也不适合守播。

另外三个实现细节：分片名可能是**毫秒**时间戳（陕西 snrtv，`1791542115000.ts`）要归一化；
可能是 `<hash>-<秒>.ts`（litenews b49 域）；master 里子清单的行要跟 `#EXT-X-STREAM-INF`
后面那条（这个 tag 是 **17** 个字符，写成 18 会永远匹配不上）。

### 长跑验证（soak）：验证「播半天后不动」到底修没修好

`--selftest` 每台只跑十几秒，**抓不到"几小时后才发作"的故障**。用户报的正是这类。
`tools/soak_play.py` 把"挂一夜听听看"变成一条命令：

```bash
python tools/soak_play.py --minutes 240            # 4 小时，静音，默认单县
python tools/soak_play.py --minutes 60 --channel 巨野
python tools/soak_play.py --minutes 200 --expect-refresh   # 顺便验证 3 小时换票会触发
```

它做三件事：
1. **把 exe 复制到独立临时目录**（`_capture/soak/<时间戳>/`）跑 —— 不碰正式的
   `state.json` / `logs`，测完自动删，正式归档不受影响；
2. 外部 `config.json` **只改音量**（默认 0 = 静音，夜里跑不吵），其它全用内置配置；
3. 每 30 秒打印一次心跳，结束给报告：开始播放 / 重建 / 换票 / 断线 / 失败的次数，
   以及**每次重建造成的静音秒数**（重建 → 下次"开始播放"的时间差）。

冒烟实测（2 分钟，单县，静音）：`播放=1 重建=0 换票=0 断线=0 失败=0 → PASS 全程无重建`。

> ⚠️ 跑之前先退出正式实例，测试期间也别启动它 —— 单实例互斥会让两边互相唤醒
> （你点图标，跳出来的是测试实例的窗口）。
>
> **判定口径**：健康长跑应该是 **0 重建**。4 小时里出现换票 0 次是对的
> （周期 3 小时，4 小时最多 1 次）；如果每几十分钟就冒一次重建，说明该台源不稳，
> 或者又踩回了 `reconnect` 那类"失败不冒泡"的老坑。

## 三、自愈能力（与安卓版完全对齐）

Win 版不是「播放器壳」，把安卓 `PlayerManager.kt` 的整套状态机搬了过来：

- **三层看门狗**（5 秒一跳）：检测音频断流
- **动态源定时换票**：`litenews://` / `hntv://` 每 `resilience.dynamic_refresh_sec`（默认 10800 = 3 小时）主动重建会话
- **指数退避**：`0 / 5 / 15 / 30` 秒，之后固定 30 秒无限循环，永不放弃
- **分级重连**：软重连（≤3 次）→ 硬重连重建会话（≤3 次）→ 休眠等待
- **网络休眠**：连续失败后每 30 秒探测一次网络，一恢复立刻重连
- **数字增益**：⚠️ **已停用**，见下方「音量」一节
- **系统音量顶满**：检测到被外力调低就顶回去（配置 `audio.force_max` 关掉）
- **统计**：今日断线 / 卡死次数跨天归零，界面常驻显示

### 音量：启动固定 100%，且音量键现在真的有效

**启动音量 100%**，每次启动都回到 100%（不记忆上次）。台号和静音状态仍会记在 `state.json` 里。
（v1.12 起从 70% 改成 100%——用户要求，`config_default.json` 与生成器同步改。）
配置项：

```json
"audio": {
  "force_max": true,
  "startup_volume": 100,     // 每次启动的初始音量
  "remember_volume": false   // true = 记住上次退出时的音量
}
```

> ⚠️ **`boost_mb` 数字增益已停用，别把它改回去。**
> 原实现是 `gain = 音量% × 10^(boost_mb/2000)` 然后 `if (gain > 1.0) gain = 1.0`。
> `boost_mb=1200` 时乘子约 **3.98**，于是**音量只要超过 26% 就被钳到 100%** ——
> 70%、80%、100% 听起来一模一样，音量键形同虚设。
> 根因是物理的：`waveOutSetVolume` 的上限就是 100%，往设备音量上乘增益只会让高位档全部饱和。
> 现在 `gain = 音量%`，线性可预期，音量键真正有效。
> 要真正的数字增益只能做在 **PCM 域**（乘采样 + 限幅），风险更高，本版没做。
> 字段保留只为与安卓版配置对齐，启动日志里也会如实记一笔「已停用」。

### 调台延迟调优（别把探测参数调回默认）

FFmpeg 默认 `probesize=5MB` / `analyzeduration=5s`，那是给点播文件的。
直播纯音频流用不着，而且实测 litenews 的 HLS 冷连接每个新主机 TLS 握手就要 2.0～2.5 秒，
再叠 5 秒分析时间，调台要等十几秒、还会顶穿 10 秒超时被判失败。

现固定为 `probesize=1500000` / `analyzeduration=3000000`（`player.c`，播放与自检两处**必须一致**，
否则自检耗时与真实播放对不上，会出「自检失败但能播」的假阳性）。

### 移植铁律（这几条都是踩过坑的，改代码前务必读）

写在 `src/player.c` 和 `src/heal.c` 的文件头注释里，核心五条：

1. **判死只能在「应该正在播出」的状态做。** 退避等待期必须完全静默，否则看门狗会在等重连时又判一次死，重连代码永远执行不到（自锁）。
2. **判死间隔必须大于封顶重试间隔。** cz-player 踩过：15 秒判死 vs 30 秒退避 = 自锁。这里是 5s 跳 × 15s 阈值 < 30s 退避，安全。
3. **只重连当前频道当前源；同台镜像回退是唯一例外（2026-10-10 用户要求）。**
   跨台的自动换台/换源仍然禁止；但**同一个台**的主源打不开时，会改试它自己的 `backup_url`（qtfm 的 lhttp ↔ lhttp-hw 双 CDN 互为镜像），成功后本会话内该台固定走镜像（sticky），镜像也失败则回到原有的自愈重试。不会来回横跳，用户切到别的台再回来才重新评估。
4. **播放路径上故意不设 `reconnect` / `reconnect_streamed`（2026-10-23）。**
   那是「播半天后一直不动」的头号根因：http 层无限内部重试且**永不返回错误**，
   `av_read_frame` 永久阻塞，线程既不死也不报错；Windows 不能强杀线程，
   每轮重建泄漏一个线程 + socket，累积半天彻底卡死。
   现在用 `seg_max_retry=2` + `http_persistent=0` 让失败快速冒泡，交给状态机重建。
   改回去之前先读 `src/player.c` 那段标红的注释。
5. **换票计时基准必须「每次解析成功就重置」，且只在 PLAYING 态判（2026-10-23）。**
   `g_app.resolve_at` 在 `play_thread` 里 `resolve_url` 返回后立刻赋值（失败置 0），
   换票分支放在 `mode != MODE_PLAYING` 的早退之后。
   少任何一条都会变成「每 5 秒一次重建」的死循环：时间戳不刷新，条件永远成立。
   安卓侧同一个坑（`sessionBuiltAt` 在 `buildPlayerWith` 入口赋值），改代码时两边一起看。

> 对 7×24 的收音机是纯损。万一某个平台票更短，失效后仍是
> 「报错 → 线程干净退出 → 看门狗重建」兜底，不会卡死。

### 支持的动态源协议

| 协议 | 解析方式 |
|---|---|
| `http(s)://...`（mp3 / m3u8） | 直连，不经 `http_get` |
| `litenews://orgid?name=台名[&kind=radio\|tv]` | 调 `app.litenews.cn`，默认先查 radio 端点再查 tv 端点，按 name 匹配定位 |
| `hntv://拼音[?cls=N]` | 调河南大象系 `xy-gw` 网关，需 `sha256(salt+timestamp)` 签名 |
| `page://https://...` | 抓 HTML 取其中第一个 `.m3u8` |
| `juyun://<id>` | 调接口后 AES-128-ECB 解密 |

签名类地址**每次播放前实时获取**，不缓存（安卓版也一样，签名几分钟就过期）。

> ⚠️ 除直链外的四种协议**全部依赖 WinHTTP**，而 WinHTTP 有三处极易踩的坑，已在
> `src/resolve.c` / `src/heal.c` 的注释里标红，改动前务必读：
> 1. `WinHttpQueryHeaders` 查状态码时 `lpdwBufferLength` **必须**是 `sizeof(DWORD)`。
>    传 0 会静默失败、状态码留在 0 → 日志只显示「HTTP 0」，看不出任何原因。
> 2. `WinHttpOpen` 的访问类型必须是 `WINHTTP_ACCESS_TYPE_DEFAULT_PROXY`。
>    `..._AUTOMATIC_PROXY` 是 Win8.1+ 的枚举，**Win7 上会让 `WinHttpOpen` 直接返回 NULL**。
> 3. 响应体要**循环读**（`QueryDataAvailable` 只报「此刻可读」的字节数），
>    单次 `WinHttpReadData` 读不全带长 `desc` 字段的 JSON。

## 五、自己编译

前置：MinGW-w64 **i686 / msvcrt** 工具链（放在 `_build/mw/`）。Win7 兼容的关键是 msvcrt 而非 ucrt。

```bash
cd D:/ningz/nzg-win
bash build.sh
```

过程：`build.sh` 生成内置配置资源 → （缺库时）编译 FFmpeg → 编译链接 → 依赖/体积验收 → `finalize.py` 改中文名。

首次会自动编译 FFmpeg 6.1.2 的 32 位静态库（约 10–20 分钟），之后增量只要几秒。

产物：`dist/守播广播.exe`（5.6 MB）

### Win7 兼容性怎么验证的（开发机是 Win11，测不出来）

`WINVER=0x0601` 只保证**编译期**用老头文件。真正的风险是：exe 是**静态导入**，
只要导入表里有一个 Win7 没有的函数，**程序在 Win7 上根本起不来**（不是某个功能不能用，
是加载器直接报错）。这类问题在 Win11 上 100% 测不出来。

所以每次出包后跑一次导入表审计：

```bash
cp "dist/守播广播.exe" _build/_audit.exe          # objdump 不认中文名
_build/mw/mingw32/bin/objdump.exe -p _build/_audit.exe > _build/imports.txt
python audit_win7_imports.py _build/imports.txt
```

2026-10-09 审计结果：**328 个导入函数全部是 XP/Vista/Win7 就有的**，无问题。
判读要点：

| 看什么 | Win7 会挂的信号 |
|---|---|
| DLL 名 | 出现 `api-ms-win-*` / `ext-ms-*` / `ucrtbase` → 链了 ucrt 或 API Set |
| kernel32 | `WaitOnAddress`(Win8) / `SetThreadDescription`(Win10) / `GetSystemTimePreciseAsFileTime`(Win8) / `GetTempPath2W`(Win10) |
| user32 | `GetDpiForWindow` / `SetProcessDpiAwarenessContext` / `AdjustWindowRectExForDpi`（全是 Win10 1607+） |
| msvcrt | 出现 `snprintf` / `vsnprintf` / `__stdio_common_*` → Win7 的 msvcrt.dll 只导出 `_snprintf` / `_vsnprintf` |

本项目实测导入的 CRT 全部是 `_snprintf` / `_vsnprintf` / `_setjmp3` / `__p__iob` 这类 XP 时代符号，
KERNEL32 最高用到 Vista 的 SRW 锁与条件变量（`AcquireSRWLockExclusive` / `InitializeConditionVariable`
/ `InitOnceBeginInitialize`），WINHTTP 只用了 10 个基础函数。

> 这只是**静态审计**，不能代替真机验证。手边有 Win7 的机器/虚拟机就跑一次，
> 确认能起窗口、有声音、能换台。

### ⚠️ Win7 真机必读：WinHTTP 的 TLS 1.2（2026-10-10 实测踩到）

真机 Win7 上日志出现：

```
[网络] 发送请求失败（err=12175）https://app.litenews.cn/v1/app/play/radio/live?orgid=51
[解析] 肥城市人民广播FM105.2 动态源解析失败，暂用原地址重试
```

`12175` = **`ERROR_WINHTTP_SECURE_FAILURE`**，即 **TLS 握手被拒**。

**根因**：Windows 7 上 **WinHTTP 的默认协议列表只有 TLS 1.0**。即使系统本身已经支持
TLS 1.2，应用也必须显式调 `WinHttpSetOption(WINHTTP_OPTION_SECURE_PROTOCOLS)` 才会去协商；
而现在的站点只收 TLS 1.2+ → 握手就崩 → 所有 `litenews://` 动态源全挂。
**这不是网络问题，源是好的** —— 同一台机器上 https 直链的台能正常播。

已修：`resolve.c` 的 `http_enable_modern_tls()` 在每次 `WinHttpOpen` 后立刻开启
TLS 1.0/1.1/1.2；`heal.c` 的 `net_probe()` 一并处理。

**为什么 FFmpeg 不用改**：FFmpeg 走 **Schannel**（`libavformat.a` 里能搜到 `schannel` 符号），
直接跟系统协商，不受 WinHTTP 那份默认协议列表约束；Schannel 能协商上 TLS 1.2，
说明**系统 TLS 1.2 本来就可用**（Win7 自带 TLS 1.2，KB3140245 只是把它默认打开）。
这组对照正好证明故障点只在 WinHTTP 那一段。

**v1.4 的修复（2026-10-10 第二轮实测）**：设了 TLS 1.2 之后**仍然 12175**，
排除了协议层 —— 实测服务器拒绝 TLS 1.0/1.1、只收 TLS 1.2，且支持 Win7 schannel
具备的 CBC 套件（ECDHE-RSA-AES128-SHA256 等）。剩下的解释只有一个：

```
*.litenews.cn ← GeoTrust TLS RSA CA G1 ← DigiCert Global Root G2（自签根）
```

**Win7 的根证书库里没有 `DigiCert Global Root G2`**。这是 DigiCert 2013 年后的新根，
平时靠 Windows Update 的 AuthRoot 机制按需下发 —— Win7 已停止支持，老机器拿不到。
WinHTTP 一验证书就 12175。我本地 openssl 连它都报 `verify error num=19`，同一个原因。

已修：`resolve.c` 的 `http_get()` 现在对**请求句柄**设置
`SECURITY_FLAG_IGNORE_UNKNOWN_CA / CERT_CN_INVALID / CERT_DATE_INVALID / CERT_WRONG_USAGE`，
即与 FFmpeg 拉流时相同的行为（FFmpeg 的 tls 协议 `verify` 默认就是 0，本来就不验证证书）。
所以解析器这边再严格也防不住什么，只是白白增加 Win7 失败率。

**如果不想关证书校验**（更讲究的做法）：把归档里的 `DigiCertGlobalRootG2.crt`
导入「受信任的根证书颁发机构」（双击 → 安装证书 → 本地计算机 → 受信任的根证书颁发机构）。
指纹核对（防中间人换证书）：
`SHA256 CB:3C:CB:B7:60:31:E5:E0:13:8F:8D:D3:9A:23:F9:DE:47:FF:C3:5E:43:C1:14:4C:EA:27:D4:6A:5A:B1:CB:5F`
这是 DigiCert 官方公布的指纹，装完不用改代码也能通。

> 附带一条：`WinHttpQueryOption` **读不回** `WINHTTP_OPTION_SECURE_PROTOCOLS`
> （会返回 `ERROR_INVALID_PARAMETER`），所以「到底协商到哪个版本」在程序里查不到，
> 只能用「请求有没有成功」间接验证 —— 别指望加个读回就能确认。

### 轻量化做了三件事（体积 16.2 MB → 5.6 MB）

1. **裁剪 FFmpeg 组件静态注册表**（`trim_ffmpeg_lists.py`）
   纯音频播放器不需要 h264/hevc/vp9/av1 等 300+ 个视频解码器。
   改 `codec_list.c` / `demuxer_list.c` / `protocol_list.c` / `muxer_list.c` 等生成文件后，
   只需要重编**包含它们的 5 个 .c**（`allcodecs.c` / `bitstream_filters.c` / `parsers.c` /
   `allformats.c` / `protocols.c`），再重打包静态库 —— 几秒钟，
   不用重跑 configure + make（那要 20 分钟）。
   注意这些 `*_list.c` 是 **`#include` 进 `allcodecs.c` 的**，不是独立编译目标，没有对应的 `.o`。
   现状：解码器 472→145、解复用器 350→29、复用器只留 `null`，
   解析器**只留音频**（视频解析器会连带把 `h264qpel` / `h264_mb` / `vc1dsp` 等 DSP 拉进来，实测约 700 KB）。
2. **`g_app` 从静态数组改成按需 malloc**（`src/config.c`）
   原来 `Channel channels[512]` 每条约 5 KB，`g_app` 一个全局变量就占 **2.45 MB** 的 `.data`
   （而且全是零），占整个 exe 的 30%。改成运行时 `calloc(实际条数)` 后降到十几 KB。
3. **静态库扁平化重打包**（`pack_ffmpeg.py`）
   `ar` 只按 basename 建成员表，`libavcodec/x86/mpegvideo.o` 会**覆盖**
   `libavcodec/mpegvideo.o`，导致 `ff_init_block_index` / `ff_mpv_common_init` 等符号全丢。
   先扁平化改名（`libavcodec/x86/foo.o` → `avcodec_x86_foo.o`）再打包即可。

### 构建环境的坑（都是踩过的）

- MinGW 工具链里的 `gcc.exe` / `python.exe` / `ar.exe` 都是**原生 Windows 程序**，
  看不懂 `/d/...` 这种 MSYS 路径（会当成 `D:\d\...`）。**构建脚本里一律用相对路径。**
- Git Bash 直传中文文件名给原生程序会走 ANSI 代码页转换，
  落盘变成 `ÊØ²¥¹ã²Ö.exe` 乱码。所以 gcc 输出统一用 ASCII 名 `shoubo-radio.exe`，
  最后由 `finalize.py` 用 Python（宽字符 API）改成 `守播广播.exe`。
- `ar` 的 `@file` 语法不支持，成员多了会超 Windows 32KB 命令行上限 →
  `pack_ffmpeg.py` 按 400 个一批用 `ar q` 追加，最后 `ranlib`。
- MSYS 无法创建符号链接 → configure 加 `export ln_s="cp -rf"`（必须带 `-r`）。
- `TMPDIR` 必须设成 MSYS 风格路径（`D:/...`），否则 configure 的 sanity test 失败。

## 六、为什么不用现成方案

- **VLC / mpv**：依赖一堆 dll，不满足「一个 exe」。

| 环境 | `[启动] 本机系统：Windows 7（6.1 SP1）`、`[启动] 程序：D://...//守播广播.exe（构建于 Oct 10 2026 14:16:22）` | 远程排查第一步：先确认是哪台机器、哪个构建（踩过：归档的是旧构建，日志格式对不上，排查被带偏） |
| 自己的 | `[断线] 打开流失败（averr=-110 Connection timed out）：https://...` | FFmpeg 错误码 + `av_strerror` 文字，能分清超时/拒绝/4XX |
| **FFmpeg 的** | `[FFmpeg] 错误：[schannel @ ...] ...`、`[FFmpeg] 警告：[http @ ...] HTTP error 502 Bad Gateway` | **失败原因的细节在这里**：TLS 握手失败、证书、HTTP 状态码都是 FFmpeg 内部用 av_log 打的。之前设了 QUIET 全吞了，等于把最有价值的证据扔掉 |

FFmpeg 这层刻意只收 WARNING 及以上 —— HLS 播放时每个分片都打一行 `Opening '...'`（DEBUG）、
mp3 的 `Skipping junk` 是 INFO，全收会把守播盒子的日志刷爆；而握手失败、HTTP 错误都是 ERROR。


**没声音？**
找 `[播放] 开始播放`。有这行说明拉流成功，再看 `[音频] waveOut 已就绪`。
两行都有但没声音，检查系统音量/输出设备。

**某个台一直重连？**
先跑 `守播广播.exe --selftest`，一次就能看出是哪几台。日志（和 `selftest.txt`）里会有：
- `[解析] litenews orgid=xxx radio 端点无「台名」，候选：A | B | C`
  —— 直接把接口给的真实频道名列出来了，照着改配置里的 `name=` 即可。
- `[解析] ... 兜底匹配到 ...` —— 台名没精确命中、靠前缀/后缀兜上了。能用，但建议把 name 改准。
- `[网络] HTTP 4xx/5xx` 或 `发送/接收响应失败（err=N）` —— 接口侧问题。
- `[断线] 打开流失败` —— 解析成功但流本身挂了，换源或剔掉。

**看门狗误判（声音断断续续）**
把配置里 `frame_stall_sec` 调大到 30。注意它必须小于 `retry_intervals_sec` 的最大值，否则触发自锁（见移植铁律第 2 条）。

**闪退？**
`main.c` 里装了崩溃捕获器，会在日志里写两行 `[崩溃]`：
异常码 + 故障地址 + 所在模块，外加 `[崩溃栈]` 的栈顶 96 个双字。
配合带符号的构建（`gcc -g`，去掉 `-s`）用 `nm` / `addr2line` 就能反查到具体函数 —— 
本项目两个致命崩溃就是这样定位的：
- `json.c` 里对**数组元素**（内联存放在 `items[]` 中的，不是独立堆块）调了 `free()`，
  等于对内层地址 free，破坏堆，等到后面某次无关分配才炸 → 已修（拆出 `json_free_inner`）。
- `swr_convert(swr, &swr_out, ...)` 传了指向 `NULL` 的指针，swresample 会把
  `out->ch[0]` 设成 NULL 然后照写 → 崩在 `_conv_AV_SAMPLE_FMT_FLT_to_AV_SAMPLE_FMT_S16`。
  必须先 `av_samples_alloc_array_and_samples()` 分配输出再传进去 → 已修。

**Win 版特有的三个静态缺陷（已修，记下来免得重犯）**

这三个都是「不崩溃、不报错、只是功能静默失效」那一类，比崩溃难查得多：

| 现象 | 根因 | 修法 |
|---|---|---|
| 所有动态源（litenews/hntv/juyun/page）全挂，直链却全好；日志只有 `[网络] HTTP 0` | `WinHttpQueryHeaders` 查状态码时 `lpdwBufferLength` 传了 0 | 改成 `sizeof(status)`（`resolve.c`） |
| 断流后进入「等待网络」，网络早通了却永远醒不过来 | `heal.c` 的 `net_probe()` 同一个写法错误 → `status` 恒为 0 → `online` 恒假 | 同上（`heal.c`） |
| 台名匹配时好时坏，同一 orgid 下有的台能过有的不过 | `query_param()` 拿**编码串下标**当**解码后下标**写 `out[]`，`%E7%A6%B9` 三字节序列留下 `out[1]/out[2]` 未初始化 | 用独立目标下标 `o` 写（`resolve.c`） |

另外 `WinHttpOpen` 用了 `WINHTTP_ACCESS_TYPE_AUTOMATIC_PROXY`，那是 Win8.1+ 才有的枚举，
**Win7 上会让 `WinHttpOpen` 直接失败**——与本项目「适配 Win7 起」的目标直接冲突，已改成 `DEFAULT_PROXY`。
这一条是纸面分析发现的（本机是 Win11 测不出来），但改掉零代价。

### v1.16.2（2026-11-03）：把「默认播放端点」的真名打进日志

v1.16.1 的心跳有了端点音量，但另一句还是废话：

### v1.16（2026-11-03）：`force_max` 从未生效过 —— 「声音很小」的真根因

**现场证据**（机房 Win7 实机日志，v1.15）：
```
[启动] 音量 100%（取配置 startup_volume），静音：否
[音频] 本机输出设备共 1 个：扬声器 (Realtek High Definition Au
[音频] 输出设备：WAVE_MAPPER → Microsoft 声音映射器
[心跳] 播放中｜近 60 秒写入 2170 块｜音量 100%｜距上次出音 0 秒
```
**程序侧 100% 正常**：未静音、音量 100、每分钟写 2170 块 PCM、设备是 Realtek（不是 HDMI）。
但人耳听到的「声音很小或者没有」。

#### 根因：那一层从来就没跑过

```c
/* 旧代码（v1.15 及更早） */
waveOutOpen(&g_main_out, WAVE_MAPPER, NULL, 0, 0, CALLBACK_NULL)
```
把 **NULL 当 `WAVEFORMATEX`** 传进去。MSDN 要求 `pwfx` 必须是有效格式，Vista+ 上该调用
**必然返回 `MMSYSERR_INVALPARAM`** → `g_main_out` 恒为 NULL → 函数在第一个分支就 `return`。

**佐证**：所有历史日志里都找不到「系统主输出音量被调低」这一行 —— 它一次都没执行过。

**更根本的问题**：即便 open 成功，`waveOutSetVolume` 在 Vista+ 也只作用于
**本进程的音频会话**（就是 `apply_waveout_volume` 已经在管的那一层），
物理上碰不到端点设备音量（右下角喇叭滑块）。想「顶满系统音量」只能用 WASAPI。

**结果**：程序把自己那一路的音量设成 100%，但 Windows 端点主音量是别人的地盘 ——
**端点音量低或静音时，程序再怎么正常写 PCM 都不会响**。

#### 修法

`player_force_max_volume()` 改用 WASAPI：
`IMMDeviceEnumerator → GetDefaultAudioEndpoint(eRender,eConsole) → IAudioEndpointVolume`，
先 `GetMute`（静音就 `SetMute(FALSE)`），再 `GetMasterVolumeLevelScalar`，
低于 95% 就 `SetMasterVolumeLevelScalar(1.0)`。

**首次读到的端点音量一定写进日志**，这是「声音小」的现场判据：
```
[音量] 系统输出端点处于静音，已取消（否则再怎么调都不会响）
[音量] 系统端点主音量 0%（这一行是「声音小」的判据）
[音量] 系统端点主音量被调低到 0%，已顶回 100%
```

⚠️ **MinGW-w64 只 extern 声明了 `CLSID_MMDeviceEnumerator` / `IID_IMMDeviceEnumerator` /
`IID_IAudioEndpointVolume`，库里没有符号**（`nm libuuid.a`、`nm libole32.a` 都搜不到），
直接引用必然 undefined reference。必须在源码里手工定义这三份 GUID
（取值来自 Windows SDK，是公开固定值），并用带后缀的变量名避开头文件那份 extern。

配套工具 `_build/setvol.exe`（`_build/setvol.c` 编出来，47KB 单文件）：
`setvol.exe` 回读、`setvol.exe 0 1` 设 0% 并静音、`setvol.exe 1 0` 设 100%。
测完 force_max 用它把机器恢复原状。

#### 附：Win7 的 `0x80090302` 也得治

同一份日志还有：
```
[FFmpeg] 错误：[tls @ 00609a40] Creating security context failed (0x80090302)
[断线] 打开流失败（averr=-1313558101）：https://lhttp.qtfm.cn/live/5022055/64k.mp3
[断线] 改试同台另一条源（镜像 backup_url）
[播放] 镜像可用：本会话内该台固定走镜像
```
`0x80090302` = `SEC_E_UNSUPPORTED_FUNCTION` —— Win7 的 schannel 默认没启用 TLS 1.2
（实现自带，只是注册表关着）。后果：**29 个 qtfm 台的 https 主源全部打不开**，
每次起播都要先失败一次再落回 http 镜像，多花 3 秒。

写法和 §19 那三条 `reg add` 等价，另外多加了一节 —— 64 位系统上 32 位进程读的

（WinHTTP 认 `DefaultSecureProtocols` 需要 KB3140245；缺这个补丁时 SCHANNEL 三节仍有效，

**结论：不改回 `persistent=1`** —— 它是 v1.13 治「播半天不动」的（防 keep-alive 静默挂死），

不是故障（见 v1.15 的归因）。

| 邹平 FM91.1 | 2 | 2.1~4.7 s | 7 秒 | 最老那一片 |
| 鄂尔多斯（nxw 直链） | 6 | 8.0 s | 48 秒 | 倒数第 3 片 |

FFmpeg 的 `live_start_index` 默认 **-3**，落点算作
`seq_no = start_seq_no + FFMAX(n_segments - 3, 0)`（`libavformat/hls.c:1753`）。
**窗口不足 3 片时会被压到最老分片** → 起播就站在过期边界上。
litenews 那 36 台窗口只有 4~6 秒、服务端每 2 秒滚一片
（连续 15 次采样实测 `Δseq=+1 / 2s`），任何一点抖动都会让最老分片滚出窗口，
于是 `skip 1`（丢 2 秒音频），之后 `cur_seq_no` 被重置回 `start_seq_no` 照常继续读 ——
**不影响出声**，纯属噪音。日志级别是 WARNING 所以一直可见，此前没人注意。

#### 二、这一版改了什么

| 改动 | 位置 | 目的 |
|---|---|---|
| `live_start_index` -3 → **-1** | `player.c: make_open_opts` | 窗口 ≥2 片时直接指到最后一片，永不贴过期边；长窗口台仍保留 1 片缓冲。比 0 稳、比 -3 准 |
| 分片过期警告 **60 秒节流** + 累计次数 | `player.c: ff_log_cb` | 不再刷屏，但保留可观测性（真异常时计数会飙高） |
| 启动日志打**音量 + 静音状态** | `main.c` | 静音是跨重启记忆的，原来恢复时零日志；这一行是「程序正常但不响」最快的判据 |
| 日志打**输出设备 + 本机设备清单** | `player.c: waveout_open` | `WAVE_MAPPER` 那行只会返回「Microsoft 声音映射器」（虚拟映射器，问不出落在哪块声卡），所以再用 `waveOutGetNumDevs` + 逐个 `waveOutGetDevCapsW` 把**全部输出设备列出来**（只在本进程打一次）—— 机器上有没有 HDMI 输出一眼可见。接显示器/电视的机器上默认设备被切到 HDMI 是高频事故，程序侧完全无感知 |
| 音量变更**补日志** | `player.c: player_set_volume` | 原来这儿一行都不记，「声音忽然变小」事后无从追查。只在值真变时记，长按不刷屏 |
| **60 秒运行心跳** | `player.c: player_heartbeat` | 一行说清：模式 / 近 60 秒写入块数 / 音量 / 是否静音 / 距上次出音 / 设备名 |

心跳的判读方式（这是它存在的全部理由）：

```
写入块数在涨 + 用户听不见   ⇒ 音频已进系统 → 查输出设备 / 端点音量 / 功放 / 线材
写入块数不涨 + 距上次出音在涨 ⇒ 解码或读流卡住 → 看门狗 15 秒内会介入并留日志
```

#### 三、为什么没有「修没声音」

`tools/probe_loudness.py`（新增）用 ffmpeg `volumedetect` 对每台拉 6 秒测真实响度：
**72/72 全部有音频**，峰值分布 −0.6 dB ~ −27.0 dB，**没有一台在推静音流**。源侧排除。

再看程序侧：`heal.c` 的看门狗只要 15 秒没往声卡写数据（读流阻塞 / 解不出帧 /
线程已死 / 首帧 60 秒未到）必然打 `[断线] 音频停滞 N 秒` + `[重连]`。
报障日志里**一条都没有** ⇒ 程序一直在正常 `waveOutWrite` ⇒ 音频被系统层吞掉。
本版能做的是把判据补进日志（设备名 + 心跳），**不是**去猜着改播放代码。

### v1.14.1（2026-11-02）：活性探测的采样窗口按分片时长自适应

v1.14 的 `--selftest --live` 报出 1 台「疑似垫片」（邹平 FM91.1）。查下来**源是活的，
是判据本身会误伤长分片台**：

| 判据 | 邹平的实际情况 |
|---|---|
| `lag = 墙钟 - 末片时间戳 ≤ 300s` | **不成立**：alivealone302 域走服务器时间轴，实测滞后 390~780 秒 |
| `Δts > 0`（两次采样分片在前进） | **不成立**：`EXTINF` 9.6 秒一片，采样只等 4 秒，窗口内不会换片 |

- 新增 `pl_last_extinf()`，从媒体列表里读最后一个分片的 `#EXTINF`；
- 第一次采样后按 `wait = max(wait_sec, EXTINF×1.2+1)`（上限 20 秒）拉长窗口，
  保证窗口跨过一个完整分片，`Δts` 才有意义；
- 日志加一行 `[活性] 采样窗口 Ns（分片 X.Xs）`，下次再出垫片先看这行就知道窗口够不够。

**顺带修的一处日志矛盾**：启动日志 `[配置] 已加载 N 个频道…当前台=X` 打的是**配置默认值**，
早于 `state.json` 恢复，于是出现「日志说鹤壁、实际在播韶关」。现在恢复状态后补一行
`[配置] 恢复上次状态：台=X`（`config.c`），两行对照即可看出真实起播台。

**验证**：
- `--selftest --live` → **72/72 通过、0 失败、0 跳过、388.1 秒**，

> 单县/巨野这类"半天后不动"则是另一回事，那是客户端死锁（见下面两条根因）。

**「播半天后一直不动」两个根因（都在客户端）**
1. **FFmpeg 无限重连把线程锁死**：旧配置 `reconnect=1 + reconnect_streamed=1`
   让 http 层在分片/连接失败后无限重试且**永不返回错误**，`av_read_frame` 永久阻塞在
   hls demuxer 内循环 —— 线程不报错也不退出，waveOut 队列播空后彻底静音；看门狗判死后
   `stop_play_thread` 又杀不掉卡在 FFmpeg 里的线程（Windows 不能强杀线程），
   每轮重建泄漏一个线程 + 若干 socket，累积半天后彻底不动。
   → **故意不设 reconnect**，改 `seg_max_retry=2` + `http_persistent=0`，
   让失败快速冒泡：报错 → 线程干净退出 → 看门狗重建 → 重新解析拿新签名。
2. **动态签名票到期**：litenews 解析出的是 100ycdn 会话票（`wsSession`/`wsIPSercert`/`wsBindIP`），
   hntv 是 `wsSecret`+`wsTime`。票过期后 CDN 常把 keep-alive 连接**静默挂住**
   （不 FIN、不发数据），比 403 更难察觉。
   → 新增 `dynamic_refresh_sec`（v1.13 取 1200 秒 = 20 分钟）：动态源每 20 分钟主动重建会话换票，
   不等它断（断了必带 15 秒静音空档）。日志类别 `[换票]`。

**自检修正**

### v1.11（2026-10-13）：实机「几天后不出声」真正根因（部署机日志定案）
- 部署机 4 天日志（log-2026-10-10 ~ 13）复盘：**v1.10 推断的「waveOut 设备
  耗尽」不成立**（零 waveOut 失败记录）。真根因是两个洞叠加：
  1. `ui.c` 的 `WM_TICK`（播放线程死亡通知）**只调了 InvalidateRect**，
     从未交给状态机 —— `ui_post_tick()` 发出去的信号被晾掉；
  2. 重建后新线程**从未拿到首帧就退出**时（重建窗口恰逢断网/源挂，
     两条源都 open 失败），`g_last_audio_at` 停在 0，看门狗
     `if (silent_sec < 0) return;`（首帧未到不判死）永远放行。
  叠加结果：状态机停在 PLAYING 但没有任何线程在播 → 零日志、零重连、
  永久无声。日志佐证：10-12 20:48:40「未能取得音频数据」后 12 小时
  应有而全无「第 2 次失败/软重连/进入等待」，10-13 08:30 手动切台进程仍活。
- 修法三层：① WM_TICK 真正调 `player_tick_watchdog()`；② 线程存活标志
  `g_thread_alive`（spawn 置 1、线程**所有退出路径**前置 0——含 resolve
  失败早退），看门狗发现 PLAYING 态却无线程立即 fail 接管（CreateThread
  失败路径同款兜住）；③ 首帧 60 秒宽限（`g_spawn_at`，resolve+双源 open
  最坏 ~45s），超时判死重建。
- v1.10 的僵尸代际修复**保留**：竞态真实存在，是另一条独立的自愈失效路径。
- **教训：播放线程的死亡通知必须到达状态机，且任何「先等等再判」的分支
  都必须有超时兜底 —— 两个半闸等于没有闸。**

### v1.10（2026-10-13）：实机「几天后不出声」根因修复 —— 僵尸线程复活开关
- **实报**：v1.6 部署机连跑数天后永久无声（2026-10-13 用户反馈）。
- **根因链**：`stop_play_thread` 只等旧线程 6s → 旧线程卡在 FFmpeg
  open(10s)/reconnect 无限循环时被迫放弃 → `g_thread_stop` 被复位 0 →
  僵尸线程从 FFmpeg 出来后继续播、永不退出 → 每个僵尸占 1 个 waveOut
  设备句柄不还 → 半死流反复重连、僵尸累积 → 数日后设备耗尽 →
  `waveOutOpen` 永远失败 → 永久无声。
- **修法**：会话代际 `g_session_gen`。stop 不复位标志；spawn 在新线程
  启动前才换代+归零；线程快照 `my_gen`，读循环与退出判定都校验 gen ——
  僵尸代际落后，从 FFmpeg 一出来立即退出。与 v1.8 WoCtx 叠加：
  僵尸既污染不了新会话、也活不过当前周期，设备零泄漏。
- **部署机验证方法**：看 v1.6 的 `logs/log-*.txt`，若大量
  `[音频] waveOut 打开失败（N）` / `无可用音频输出设备` 即坐实；
  日志按天保留 7 天，故障日的文件最有价值。

### v1.8（2026-10-12）：waveOut 会话线程局部化，根除僵尸线程污染
- **问题**：`stop_play_thread` 只等旧线程 6 秒，而 `avformat_open_input` 超时 10 秒、
  FFmpeg `reconnect=1` 遇「TCP 活但无数据」的半死流还会无限内部重连 ——
  旧线程（僵尸）拖尾退出时 `waveout_close` 操作**全局**设备/槽位，
  恰好关掉或乱写新会话刚建好的资源 → 反复无声、要多绕几轮重连才收敛，
  是长跑（7×24 挂机）场景下最大的不稳定源。
- **修法**：设备 + 4 槽收进线程私有的 `WoCtx`（`play_thread` 栈上），
  `waveout_open/close/recycle/free_slot` 全部带 ctx 参数、不碰全局；
  全局 `g_wo` 退化为「UI 音量键的当前活跃设备句柄」（新会话 open 成功时指向它，
  close 时只有 `g_wo == 本会话设备` 才摘除）。僵尸线程死活都影响不到新会话。
- `player_stop` 的兜底 close 改为只 `waveOutReset(g_wo)`（UI 线程不知道 ctx 归属，不代关）。
